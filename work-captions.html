A bounded visual language

A theme is MotionDSL: typed, immutable data describing typography, design tokens, word roles, decorations, responsive layout and animation. Behaviours target roles — active, spoken, keyword or hero words — trigger on word or page boundaries, and animate supported properties: scale, opacity, translation, rotation, marker progress and accent colour.

The motion vocabulary includes easing curves, staggers from the start, end, centre or edges, alternating transforms, bounded travelling waves, beat-specific movement for a hook, turn or payoff, and responsive breakpoints for portrait, square and landscape. There are no executable expressions, URLs or file paths; unknown fields and unsupported capabilities produce diagnostics.

Compiling into the editor

The compiler parses the theme, checks capabilities and bundled fonts, resolves tokens and responsive parameters, and lowers the program into the caption engine’s existing style specification. It is applied through an ordinary authoring command, so a generated theme is edited with the same controls, saved-style gallery and word patches as a manual one.

Each theme version keeps its canonical source, hash and compiler version. Revisions append immutable versions with lineage, so “less bounce” revises the program without erasing its predecessor.

Repairing generated programs

The Caption Design Agent proposes at most three themes per call and supports up to twelve per request. Compiler diagnostics go back to the model with instructions to return a complete corrected theme, within three repair rounds; if only some variants succeed, the valid subset is returned.

Two failure modes needed deterministic checks. A valid two-percent scale change looks static, so a review measures each track’s deviation and duration and rejects imperceptible motion. And different colours can hide identical animation, so variants are compared by the Jaccard overlap of their motion graphs — target, trigger and property — and rejected above 0.6. That measures structural variety, not artistic quality.

Editorial structure drives animation

Before styling, the Caption Director writes a direction plan: ordered segments with narrative roles and intensity, emphasis with reasons, and a visual direction. These become editable page boundaries, word patches and motion beats. A validator flags excessive emphasis or too many focal phrases; consecutive emphasised words can form a phrase of up to four words, so “ten thousand dollars” stays one unit. Intensity modulates motion strength, and a payoff can move differently from its setup.

Preview and export must agree

Captions are evaluated in TypeScript for the browser preview and in Python for native export. A shared fixture protocol compares every field, allowing numeric differences below 1e−6, and new fixtures are installed only when both implementations agree.

Rendered comparison still found defects the data tests missed: word plates that did not follow motion, shadows that stayed opaque while words faded, layout that reserved space for only one font variant, and bottom-anchored captions that exported below their preview position — one case by 113 pixels. Fixes covered those plus right-to-left spacing, outline-aware gaps and space for the largest animated footprint. Word scale is capped at 2.2×, and geometry checks reject themes whose peak motion leaves the frame.

Implementation notes

The research loop

Generate, render, inspect the failure, add the missing representation or validation, and verify both implementations. Most of the language’s current shape came from that loop rather than up-front design.

Scope

Fixture parity checks evaluation, not pixel-identical painting; typography and rendering still need rendered inspection. The language deliberately has no arbitrary code, shaders or 3D.
