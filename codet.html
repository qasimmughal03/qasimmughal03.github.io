Overview

At Codet AI I worked on the layer behind its software-engineering agents that decides what they know and how they use it: how a codebase and its domain are represented, how an agent finds the context a task needs, and how its output is checked before it is trusted.

This page covers the problems, my contributions and the reasoning behind them. Each contribution is marked Built where I implemented it, or Explored where I prototyped, studied or compared an approach.

My contributions

  • Built The ontology-backed knowledge-representation layer, which I owned: typed entities, relationships and constraints for code and domain knowledge, stored on relational infrastructure (YugabyteDB).
  • Built An EBNF-defined graph-query language and validation of LLM-generated graph structures with datatype, cardinality, relationship and OCL-style rules.
  • Built Hybrid context retrieval combining lexical and keyword matching, semantic similarity, multi-hop graph traversal, PageRank-style scoring and fused ranking.
  • Built Stateful LangGraph coding-agent workflows: ts-morph/AST repository analysis, repository code graphs, requirements-to-Gherkin test generation, compiler validation, guarded execution and diagnostic repair loops.
  • Explored Weisfeiler–Lehman and Poincaré graph embeddings; HippoRAG- and AnchorRAG-style graph retrieval; capturing agent execution events and turning recurring patterns into reusable skills.

Theme A

AI coding agents

The problem

A coding agent has to change a real codebase: understand where new code belongs, act through tools, and produce changes that compile and meet the requirement. A language model alone guesses at all three.

What I worked on

Built Stateful agent workflows in LangGraph, where each step has explicit state and permitted transitions. Repository context comes from AST analysis with ts-morph — symbols, imports and dependencies — organised as a code graph rather than raw text. Requirements are turned into Gherkin scenarios, so "done" is an executable behaviour, not a judgement. Changes pass compiler validation and guarded execution; failures produce diagnostics that feed a bounded repair loop.

Explored Recording agent execution events and extracting recurring successful patterns into reusable skills, so the agent does not rediscover the same procedure each time.

Engineering reasoning

Split responsibilities by reliability: the model plans and writes; deterministic tools — parser, compiler, tests — supply ground truth. Validation turns agent output from plausible into falsifiable, and finite-state execution policies keep a long-running agent from wandering.

Technical detail: why BDD scenarios for agents

Gherkin (Given/When/Then) gives a requirement a structured, human-readable form that can also be executed. For an agent, that turns an ambiguous instruction into acceptance criteria it can test against before reporting success — and gives a reviewer the same criteria to read.

Theme B

Knowledge representation and retrieval

The problem

The context an agent needs is spread across files and concepts, connected by relationships — calls, imports, inheritance, domain rules — that a nearest-neighbour vector search does not preserve. And identifiers such as function names are often out of vocabulary for embedding models.

What I worked on

Built An ontology-backed knowledge graph: typed nodes, edges and constraints, modelled on a relational database, with an EBNF-defined query language for structured operations (Boolean predicates, comparisons, relationship traversal). Retrieval combined signals, each covering a different failure mode: lexical and keyword matching for exact identifiers and out-of-vocabulary terms; semantic similarity for paraphrased intent; graph traversal for multi-hop relationships; PageRank-style scores for structural importance; and fused ranking to merge them.

Explored Graph embeddings: Weisfeiler–Lehman representations for structural similarity, and Poincaré (hyperbolic) embeddings for hierarchies such as package and type trees.

Engineering reasoning

No single retrieval signal is sufficient; the useful question is which signal is reliable for which kind of request, and how to combine them. Keeping graph data in relational storage keeps one transactional store and familiar operations, at the cost of expressing traversal through queries — one reason a typed query language and structured operations were worth building.

Technical detail: what each graph-embedding method contributes

Weisfeiler–Lehman refines each node's label using its neighbours' labels over several rounds, so nodes in the same structural role end up with similar signatures even when their names differ. Poincaré embeddings place nodes in hyperbolic space, where distance from the centre naturally encodes depth in a hierarchy, so tree-like structures embed with low distortion in few dimensions.

Theme C

Reasoning and agent learning

The problem

LLM-only reasoning has no guarantee of consistency: a model can produce a graph that violates the ontology, or answer a multi-hop question from the wrong starting entity. It also forgets how it solved similar problems before.

What I worked on

Built Symbolic constraints around neural components: LLM-generated graph structures are validated against datatype, cardinality, relationship and OCL-style rules before agents use them, and structured queries go through a grammar rather than free text.

Explored Graph-based context organisation informed by HippoRAG and AnchorRAG — propagating relevance from query-linked entities, and choosing good anchor entities when the query does not name them exactly. Agent memory built from execution history, with recurring procedures abstracted into reusable skills.

Engineering reasoning

Use the model for flexible interpretation and the symbolic layer for guarantees. Constraints catch malformed knowledge at the boundary instead of letting it surface later as a confident wrong answer.

Selected problems

How does an agent find context spread across many files?
Combine exact-match, semantic and structural signals, then rank connected evidence rather than isolated matches.
How do you trust a knowledge graph an LLM helped build?
Validate it against an explicit ontology and constraints before any agent reads from it.
How do you know an agent's change is correct?
Turn the requirement into executable scenarios, and let the compiler and tests — not the model — decide.

Related research

Selected papers that provide technical background for this work.

  1. HippoRAG: Neurobiologically Inspired Long-Term Memory for Large Language Models

    Gutiérrez, Shu, Gu, Yasunaga, Su · NeurIPS 2024 · arXiv:2405.14831

    Contribution
    Builds a knowledge graph from a corpus and uses Personalized PageRank from query entities to retrieve evidence for multi-hop questions in a single step.
    Problem
    Multi-hop context selection: the evidence an agent needs is often several relations away from the query.
    Connection
    Informed how I thought about graph-propagated relevance (PageRank-style scoring) on top of lexical and semantic matching. A follow-up, HippoRAG 2 (arXiv:2502.14802, ICML 2025), extends the approach.

  2. Towards Open-World Retrieval-Augmented Generation on Knowledge Graph: A Multi-Agent Collaboration Framework (AnchorRAG)

    Xu, Li, Tang, Wang, Zhang · 2025 · arXiv:2509.01238

    Contribution
    Proposes AnchorRAG: an agent predicts candidate anchor entities by matching query terms to graph nodes, and retriever agents explore multi-hop paths from each anchor in parallel.
    Problem
    Linking a natural-language request to the right starting points in a graph when there is no exact entity match.
    Connection
    Relevant to entity linking and out-of-vocabulary queries over a code knowledge graph.

  3. Weisfeiler-Lehman Graph Kernels

    Shervashidze, Schweitzer, van Leeuwen, Mehlhorn, Borgwardt · JMLR 12, 2011

    Contribution
    Graph similarity from iterative neighbourhood relabelling (the WL test), with runtime linear in the number of edges.
    Problem
    Comparing local structure: two code elements can play the same structural role without sharing names.
    Connection
    Basis for the Weisfeiler–Lehman structural representations I investigated for structure-aware relevance.

  4. Poincaré Embeddings for Learning Hierarchical Representations

    Nickel, Kiela · 2017 · arXiv:1705.08039

    Contribution
    Embeds symbolic data in hyperbolic space (the Poincaré ball), representing hierarchies with far fewer dimensions than Euclidean embeddings.
    Problem
    Representing hierarchies — packages, modules, classes and ontology type trees.
    Connection
    Investigated as a way to encode hierarchical position alongside lexical and semantic signals.

  5. SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering

    Yang, Jimenez, Wettig, Lieret, Yao, Narasimhan, Press · 2024 · arXiv:2405.15793

    Contribution
    Shows that the interface an agent uses to view files, navigate a repository and run tests strongly affects how well it solves real software tasks.
    Problem
    Designing the tools and feedback loop of a coding agent.
    Connection
    Context for the same design question in my work: give the agent structured repository access and deterministic checks rather than raw text.

  6. Voyager: An Open-Ended Embodied Agent with Large Language Models

    Wang, Xie, Jiang, Mandlekar, Xiao, Zhu, Fan, Anandkumar · 2023 · arXiv:2305.16291

    Contribution
    An agent that accumulates a library of verified, executable skills from its own experience and reuses them on new tasks.
    Problem
    Turning successful agent behaviour into reusable procedures.
    Connection
    Conceptual background for the execution-event capture and skill extraction I explored.

What I took away

  • Retrieval quality is a design problem across several signals, not a choice of embedding model.
  • Explicit structure — ontologies, typed queries, constraints — makes agent behaviour inspectable and testable.
  • The most reliable agents are the ones whose success is decided by deterministic checks.
  • Research ideas are most useful when adapted to a concrete failure mode, and evaluated against simpler baselines.
